# SentinelRAG — System Architecture

## 1. Overview

**Project:** SentinelRAG  
**Domain:** SOC Operations and Cybersecurity Incident Response  
**Primary source language:** English

SentinelRAG is an evidence-grounded RAG system that retrieves trusted cybersecurity guidance from NIST, CISA, OWASP, and MITRE ATT&CK, reranks the evidence, and generates answers that remain tied to visible source material.

The implemented architecture has two paths:

1. **Offline ingestion** — collect, clean, chunk, embed, and index source material.
2. **Online query** — embed the question, run hybrid retrieval, rerank, and generate from the strongest five evidence passages.

## 2. Final high-level architecture

### Offline ingestion

    26 verified cybersecurity sources
        -> PDF / HTML / MITRE STIX extraction
        -> conservative text cleaning
        -> structure-aware recursive chunking
        -> ~350 tokens per chunk + ~60-token overlap
        -> deterministic chunk IDs + source metadata
        -> multilingual-e5-small passage embeddings
        -> ChromaDB vector index
        -> BM25 lexical index

Final evaluation index:

- ChromaDB chunks: **7,570**
- BM25 chunks: **7,570**
- deterministic chunk IDs shared across both indexes

### Online query

    Authenticated user
        -> Streamlit
        -> E5 query embedding
        -> Vector Top-25 + BM25 Top-20
        -> Reciprocal Rank Fusion (RRF)
        -> Cohere rerank-v3.5
        -> final Top-5 evidence
        -> Cohere command-r7b-12-2024
        -> grounded answer + native citation metadata + visible evidence

In production, query embeddings are generated by a separate private Railway service using a prebuilt OpenVINO FP16 E5 artifact. Local development can still use the SentenceTransformers implementation.

## 3. Domain and source collection

The corpus contains **26 verified authoritative sources**:

- 17 PDF documents
- 8 HTML sources
- 1 structured MITRE ATT&CK dataset

Publishers:

- NIST
- CISA
- OWASP
- MITRE ATT&CK

The complete source inventory is stored in `data/sources_manifest.csv`.

### Why these sources

Incident-response guidance can affect containment, recovery, evidence preservation, logging, identity security, and forensic decisions. SentinelRAG therefore prioritizes official standards, government guidance, and established security knowledge bases rather than random blogs.

## 4. Extraction

PDFs are extracted page-by-page with **PyMuPDF** so page numbers can be preserved for evidence attribution.

HTML pages are cleaned with **BeautifulSoup**, removing scripts, styles, navigation, headers, footers, breadcrumbs, and unrelated interface text.

MITRE ATT&CK is processed from structured STIX/JSON data so techniques, sub-techniques, detection strategies, and analytics can preserve identifiers such as `T1055` and `T1055.011`.

### Why not flatten everything into one text file

Flattening the whole corpus would lose useful structure and make source/page attribution harder. The chosen extraction path preserves metadata that the retrieval system and UI can expose later.

## 5. Chunking strategy

SentinelRAG uses **structure-aware recursive chunking**.

Configuration:

- maximum chunk size: approximately **350 tokens**
- overlap: approximately **60 tokens**
- deterministic chunk IDs
- preserved source/page/section metadata

### Why ~350 tokens

Cybersecurity documents frequently contain procedures, controls, and technical explanations. Very large chunks can mix unrelated topics and reduce retrieval precision. Very small chunks can separate an instruction from its rationale or conditions.

Around 350 tokens provides a practical balance between local context and retrieval specificity.

### Why ~60-token overlap

Overlap protects context that crosses a split boundary. A much larger overlap would increase index size, embedding work, and duplicate retrieval results without proportional benefit.

### Why deterministic chunk IDs

Stable chunk IDs allow the 30 Golden Questions to refer to the same evidence after a clean rebuild. This supports reproducibility, debugging, and evaluation integrity.

## 6. Embedding model

Model: `intfloat/multilingual-e5-small`  
Dimension: **384**  
Document prefix: `passage:`  
Query prefix: `query:`  
Normalization: enabled

### Why multilingual-e5-small

E5 is designed for retrieval and separates query and passage representations. Semantic retrieval matters because a question can use different wording from the source while expressing the same concept.

The small model is CPU-friendly, which is important for a low-cost Railway deployment. Its multilingual training also leaves room for future Arabic questions.

### Why not a larger embedding model

A larger model could improve some retrieval cases but would increase memory, startup time, and deployment cost. SentinelRAG prioritizes a model that can run reliably on modest resources.

## 7. Production embedding service

Production uses a separate Railway service named **sentinel-embed**.

The service:

- loads a prebuilt OpenVINO FP16 E5 artifact
- performs float32 inference
- accepts one query at a time
- returns a normalized 384-dimensional float32 vector
- runs privately behind the public Streamlit application

### Why split embeddings from Streamlit

Keeping embedding-model inference in the same process as Streamlit created unnecessary memory pressure during deployment work. Separating the model keeps the public web process smaller and avoids loading PyTorch/SentenceTransformers in the production web process.

This deployment optimization does not change the retrieval model or the stored index.

## 8. Vector database

SentinelRAG uses **ChromaDB** with persistent storage under `data/index/`.

### Why ChromaDB

The final corpus contains 7,570 chunks, which does not justify distributed vector infrastructure.

ChromaDB provides:

- persistent vector storage
- cosine similarity search
- metadata alongside vectors
- simple Python integration
- easy local reproducibility

### Alternatives

**FAISS:** strong vector search, but metadata and persistence would require more custom application logic.

**Elasticsearch/OpenSearch:** powerful but operationally heavy for this corpus size.

**Managed vector database:** would add credentials, network dependency, and cost without a clear need at this scale.

## 9. BM25 lexical index

SentinelRAG uses **rank-bm25** on the exact same chunks as ChromaDB.

### Why BM25

Cybersecurity includes exact identifiers and terminology such as:

- ATT&CK technique IDs
- CVE identifiers
- OAuth
- MFA
- protocol names
- malware names

Pure semantic search can under-rank exact strings. BM25 complements the semantic retriever.

## 10. Hybrid retrieval and fusion

Final retrieval configuration:

- Vector Top-K: **25**
- BM25 Top-K: **20**
- RRF constant: **60**
- final evidence after reranking: **5**

The vector and BM25 rankings are merged with **Reciprocal Rank Fusion**.

### Why RRF

Vector similarity and BM25 scores are on unrelated scales. RRF uses rank positions instead of attempting to normalize incompatible raw scores. It also rewards chunks that rank well in both retrievers.

## 11. Reranking

Fused candidates are sent to **Cohere rerank-v3.5**. The system keeps the five highest-ranked passages.

### Why remote reranking

A local CrossEncoder would add another local model and more memory pressure. Remote reranking keeps the local deployment lighter while preserving a dedicated relevance-ranking stage.

### Why Top-5

The capstone evaluates Recall@5, and five passages give useful evidence diversity without flooding the generator with lower-ranked context.

## 12. Generation and grounding

Generation model: `command-r7b-12-2024`.

The system prompt requires the model to:

- answer only from retrieved evidence
- avoid inventing facts, procedures, standards, sources, or pages
- state clearly when evidence is insufficient
- distinguish limitations
- treat retrieved text as reference material rather than executable instructions

The Top-5 passages are passed as documents to Cohere Chat. Native citation metadata is extracted and shown in the UI.

## 13. Authentication and interface

The UI uses **Streamlit** and shared-password authentication from `APP_PASSWORD`.

The application displays:

- grounded answer
- native citation information
- exactly five evidence passages
- source IDs
- page numbers or ATT&CK section IDs
- rerank scores
- evidence text

Secrets are stored in environment variables rather than hard-coded in the repository.

## 15. Retrieval evaluation

The project uses **30 manually verified Golden Questions**.

A question is a Recall@5 hit when at least one labeled gold chunk appears in the final reranked Top-5.

### Baseline

Vector Top-20 + BM25 Top-20:

- hits: 24 / 30
- Recall@5: 80.00%
- strict `>80%` requirement: **not satisfied**

### Final

Vector Top-25 + BM25 Top-20:

- hits: 25 / 30
- Recall@5: **83.33%**
- requirement: **passed**

The improvement widened semantic retrieval from 20 to 25 before fusion and reranking. Golden labels were not changed to manufacture a better result.

## 18. Architecture tradeoffs

Advantages:

- authoritative evidence
- semantic + lexical retrieval
- exact-identifier support
- deterministic evaluation labels
- visible source attribution
- lightweight public web process
- measurable retrieval and generation quality

Accepted limitations:

- Cohere is an external dependency for reranking and generation
- the single-worker embedding service can become a concurrency bottleneck
- the corpus must be refreshed as cybersecurity guidance changes
- ChromaDB is appropriate at this scale but is not a distributed search platform
- shared-password authentication is suitable for a capstone, not enterprise IAM
- evaluation results do not guarantee performance on every unseen cybersecurity question

## 19. Architecture priorities

SentinelRAG prioritizes:

1. authoritative evidence
2. retrieval accuracy
3. source attribution
4. reproducibility
5. low deployment complexity
6. measurable evaluation
7. defensive cybersecurity use
8. cost awareness
